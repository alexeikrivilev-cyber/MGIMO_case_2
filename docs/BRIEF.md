## Продукт

Рабочий прототип **«Цифровой деканат будущего»** — личный кабинет студента для **Удмуртского государственного университета (УдГУ)**, прототип «под внедрение». Полный кейс конкурса: `docs/CASE.md` (источник истины по требованиям).

Смысл: разбросанная учебная жизнь студента (расписание на сайте, оценки в отдельной системе, справки в очереди, объявления в чатах) собирается в одно мобильное, безопасное, приятное место.

ВУЗ в прототипе — УдГУ: название и реалии вуза использовать можно (кейс это позволяет), НО данные остаются синтетическими, никаких реальных персональных данных, никакого подключения к реальным системам вуза. Логотип УдГУ не использовать — сделать собственный знак, перекликающийся по идее. Баннер «учебный концепт, не официальный сервис» обязателен.

## Обязательное ядро (без него работа неполная)

1. Вход и профиль: профиль студента (ФИО, факультет, направление, курс, группа). См. также «Регистрация и верификация» — это часть ядра.
2. Расписание: занятия на сегодня и на неделю, аудитория и преподаватель, заметные изменения и переносы.
3. Успеваемость: оценки и зачёты по дисциплинам, сессия, понятная картина «как у меня дела с учёбой».
4. Заявки и справки: заказ справки или подача заявления онлайн и статус заявки (интеграция с деканатом).
5. Уведомления: новости и объявления деканата, напоминания о дедлайнах и изменениях.

## Расширенные требования (v2 — под внедрение в УдГУ)

### 1. Регистрация и верификация (часть ядра)
- Вход по логину/паролю университетской учётной записи (как сейчас).
- Регистрация через **VK ID / MAX / Telegram** (OAuth-кнопки; в прототипе — эмуляция согласия, без реальных ключей) с **обязательным** указанием ФИО и группы.
- **Загрузка фото студенческого билета** → распознавание → **сверка с данными университета** (в прототипе — синтетический реестр + мок-распознавание; реальные фото и ПДн не обрабатывать).
- **Только после успешной верификации** открываются: оценки (успеваемость) и переписка с преподавателями.
- До верификации студент видит свой профиль, расписание своей группы и общедоступную информацию.
- Фото студбилетов хранить безопасно: приватное хранилище, доступ только владельцу/верификатору, никаких публичных ссылок; в коде и браузере — никаких секретов.

### 2. Расписание преподавателей
- Студент видит расписание преподавателей (пары, консультации, часы приёма) — чтобы понимать, когда можно подойти.
- Преподаватель видит своё расписание и свои группы.

### 3. Статус «болею»
- Студент отмечает болезнь (указывает период; при желании — прикрепляет справку).
- Статус интегрируется с «системой университета» (в прототипе — синтетический реестр: деканат/преподаватели видят, кто болеет; отражается в учёте посещаемости у преподавателя).
- Уведомления преподавателям/в деканат о новых статусах.

### 4. Переписка студент ↔ преподаватель
- Студент пишет преподавателю; преподаватель видит, кто пишет (верифицированная личность: ФИО, группа) — поэтому переписка только для верифицированных.
- Диалоги, непрочитанные, уведомления. Преподаватель отвечает.

### 5. Тематический ИИ (два сценария, оба понятны пользователю)
- **Для студента**: помощник в учёбе — что подтянуть, как закрыть долги (план по долгам с опорой на его оценки и расписание), напоминания, ответы по его данным.
- **Для преподавателя**: RAG-ассистент — преподаватель загружает учебный план (и материалы), агент подсказывает: сопоставление тем плана с долгами/вопросами студентов, ответы по плану.
- ИИ работает только с данными владельца сессии; ключи LLM — только env на сервере, без fallback-утечек; при отсутствии ключа — детерминированный режим.

### 6. Кабинет сотрудника деканата (как было)
- Обработка заявок/справок, публикация объявлений, переносы пар; верификация студбилетов (очередь на проверку); просмотр статусов «болею».

### 7. MCP-сервер для агентов деканата
- Инструменты для агентов сотрудников: расписание (группы/преподавателя), успеваемость, заявки, объявления, статусы болезней. Заказчик назвал это фичей «на поверхности» — но каждая фича должна быть понятна пользователю и оправдана.

## Жёсткие ограничения (требования кейса)

- Работающий прототип по ссылке в браузере (не макет). Основные сценарии проходятся: регистрация/вход → расписание → оценки → подать заявку → увидеть статус.
- Мобильная версия: всё работает на экране от 360 px.
- Только вымышленные данные (ФИО, оценки, зачётки, студбилеты — синтетика). Не подключать реальные системы вуза.
- На сайте понятно, что это концепт для конкурса, не официальный сервис. Логотип вуза не использовать.
- Сторонний код/шрифты/иконки — только с подходящей лицензией.
- Безопасность: студент видит только свои данные (подмена ID в URL не открывает чужие); пароли не хранятся в открытом виде; ключи и пароли сервисов не в коде и не в браузере пользователя.
- Доступность для жюри: открывается из России без VPN, работает до 28 ноября 2026. Хостинг — Helsinki VPS (177.3.196.28).
- Тестовые аккаунты: минимум 2 студента с разными данными + преподаватель + сотрудник деканата.

## Приоритеты (порядок важен)

- **P1 — ядро**: монорепо + PostgreSQL + синтетика (УдГУ); вход по логину/паролю + регистрация через VK/MAX/Telegram с верификацией по студбилету; профиль; расписание групп; расписание преподавателей; успеваемость (после верификации) + сводка; заявки/справки со статусами; уведомления; статус «болею»; серверная авторизация владения данными + анти-IDOR.
- **P2 — глубина**: кабинет сотрудника деканата (заявки, объявления, переносы, верификация студбилетов, статусы болезней); переписка студент↔преподаватель; AI-ассистент студента (долги/учёба); AI-ассистент преподавателя с RAG по учебному плану; MCP-сервер.
- **P3 — качество**: дизайн-система (знак УдГУ-концепт), пустые состояния, ошибки, загрузка, скорость, WCAG AA, тёмная тема, PWA.
- **P4 — сдача**: деплой Helsinki VPS (PO будет жёстко проверять — готовить основательно), тестовые аккаунты, документ процесса со скриншотами, репозиторий, видео ≤5 мин (по желанию).

## Технические ограничения (установлены PO)

- Ориентир стека: Next.js/TypeScript, PostgreSQL, Docker; прод — Helsinki VPS.
- **Архитектура — высокого, поддерживаемого уровня** (требование PO): чистые границы модулей, переиспользуемое ядро, миграции под контролем, типизация end-to-end, тесты на критичные пути (авторизация/владение данными).
- Авторизация — своя (argon2id + httpOnly-сессия) или эквивалент с полным контролем безопасности.
- Секреты — только env на сервере.
- Git: мастер-ветка `master`, фичи — ветками, мёрж после QA-гейта.

## Критерии приёмки PO (как проверяю)

1. Открывается по URL извне; сценарии ядра проходятся без ошибок.
2. Тестовые аккаунты (2 студента + преподаватель + сотрудник) работают; данные разделены — student2 не видит заявки/оценки/переписку student1 (проверяю подстановкой ID).
3. Регистрация: без верификации студбилета оценки и переписка недоступны; после (мок-)верификации — доступны.
4. Мобильный вид 360 px корректен; есть баннер «концепт».
5. В репозитории — README (запуск), документ процесса, засеянные синтетические данные.
6. Никаких секретов в коде; пароли — только хеши.
