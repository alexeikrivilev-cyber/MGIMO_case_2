## Продукт

Рабочий прототип **«Цифровой деканат будущего»** — личный кабинет студента вымышленного Университета «Горизонт». Полный кейс конкурса: `docs/CASE.md` (источник истины по требованиям).

Смысл: разбросанная учебная жизнь студента (расписание на сайте, оценки в одной системе, справки в очереди, объявления в чатах) собирается в одно мобильное, безопасное, приятное место.

## Обязательное ядро (без него работа неполная)

1. Вход по логину/паролю + профиль студента (ФИО, факультет, направление, курс, группа).
2. Расписание: сегодня и неделя, аудитория, преподаватель, заметные переносы и отмены.
3. Успеваемость: оценки и зачёты по дисциплинам, сессия, понятная сводка «как у меня дела».
4. Заявки и справки онлайн + статус заявки.
5. Уведомления: объявления деканата, дедлайны, изменения расписания.

## Жёсткие ограничения (требования кейса)

- Работающий прототип по ссылке в браузере (не макет). Основные сценарии проходятся: войти → расписание → оценки → подать заявку → увидеть статус.
- Мобильная версия: всё работает на экране от 360 px.
- Только вымышленные данные (ФИО, оценки, зачётки — синтетика). Не подключать реальные системы вуза.
- На сайте должно быть понятно, что это концепт для конкурса, не официальный сервис. Логотип вуза не использовать (можно свой знак).
- Сторонний код/шрифты/иконки — только с подходящей лицензией.
- Безопасность: студент видит только свои данные (подмена ID в URL не открывает чужие); пароли не хранятся в открытом виде; ключи и пароли сервисов не в коде и не в браузере пользователя.
- Доступность для жюри: открывается из России без VPN, работает до 28 ноября 2026. Хостинг любой (есть Helsinki VPS 177.3.196.28).
- Тестовые аккаунты: минимум 2 студента с разными данными; если есть кабинет сотрудника — и его аккаунт.

## Внутренний дедлайн и режим

- Владелец установил внутренний дедлайн: **21 ноября 2026** (внешний — 28 ноября). Работа без остановок, этапы идут один за другим.
- Режим автономии: PO не участвует в повседневной работе. Блокеры решаются на месте (например, доступов к реальной БД нет — данные синтетические by design).

## Приоритеты (порядок важен)

- **P1 — ядро** (пункты выше) + серверная авторизация владения данными + защита от IDOR.
- **P2 — глубина** (после рабочего ядра): кабинет сотрудника деканата (заявки, объявления, переносы пар); AI-ассистент в кабинете (отвечает по данным студента); **MCP-сервер для агентов деканата** (расписание/оценки/заявки/объявления через протокол MCP) — заказчик назвал это фичей «на поверхности», но каждая фича должна быть понятна пользователю и оправдана.
- **P3 — качество**: цельный современный дизайн, пустые состояния, ошибки, загрузка, скорость, доступность (WCAG AA), тёмная тема, PWA.
- **P4 — сдача**: деплой (Helsinki VPS), тестовые аккаунты, документ процесса со скриншотами (проблема, инструменты ИИ, ключевые промпты, как устроены вход/данные/защита), репозиторий, при желании видео ≤5 мин.

## Технические ограничения (установлены PO)

- Стек на выбор Hermes, но с ориентиром: Next.js/TypeScript, PostgreSQL, Docker; прод — Helsinki VPS ( Docker Compose).
- Авторизация — своя (argon2id + httpOnly-сессия) или эквивалент с полным контролем безопасности.
- Секреты — только env на сервере.
- Git: мастер-ветка `master`, фичи — ветками, мёрж после QA-гейта.

## Критерии приёмки PO (как проверяю)

1. Открывается по URL извне; сценарии ядра проходятся без ошибок.
2. Тестовые аккаунты (2 студента + сотрудник) работают; данные разделены — student2 не видит заявки/оценки student1 (проверяю подстановкой ID).
3. Мобильный вид 360 px корректен; есть баннер «концепт».
4. В репозитории — README (запуск), документ процесса, засеянные синтетические данные.
5. Никаких секретов в коде; пароли — только хеши.
