# Документ процесса создания

> proj-3311 «Цифровой деканат будущего» — прототип личного кабинета студента УдГУ.
> Этот документ — для жюри (критерий 2 кейса): проблема, инструменты ИИ, ключевые
> промпты, этапы, ошибки и то, что делалось вручную.
> Оперативный лог со всеми деталями и выводами команд — `docs/LOG-hermes.md`.

## 1. Какую проблему решаем

Учебная жизнь студента разбросана: расписание — на сайте вуза, оценки — в отдельной
системе, справки — через очередь в деканате, объявления — в чатах и на почте. С телефона
каждое из этих мест неудобно, а вместе — невыносимо: чтобы ответить на вопрос «что у меня
завтра и всё ли со мной в порядке», нужно 4–5 переходов между системами.

**Задача кабинета:** за 10 секунд с телефона понять, что сегодня по учёбе и всё ли в
порядке, и решить routine-вопросы (справка, отметка о болезни) не выходя из дома.

**Почему выбраны именно эти разделы:** ядро определено кейсом (вход/профиль, расписание,
успеваемость, заявки, уведомления). Сверх ядра добавлены разделы, которые снимают
конкретную боль: **верификация по студбилету** (деканат не должен выдавать оценки и не
должен пускать в переписку кого попало), **расписание преподавателей и часы приёма**
(«когда можно подойти» — вопрос, на который сегодня ответа нет), **статус «болею»**
(сейчас студент бегает с бумажкой), **«леверидж»** (сколько баллов нужно до целевой оценки)
и **«чей ход»** по заявке (статус «на рассмотрении» не говорит, ждут студента или нет).

## 3. Архитектура и стек (решения и почему)

| Слой | Выбор | Почему |
|---|---|---|
| Монорепо | npm workspaces | Одна кодовая база UI + API + домен, общие типы |
| Frontend + BFF | Next.js 15.5 (App Router, TypeScript) | Ориентир PO; SSR + Route Handlers в одном месте |
| Стили | Tailwind CSS 4 + токены в `packages/ui` | Быстро, консистентно, мобильный-first |
| БД | PostgreSQL 16 + Prisma 7.10 + pg-адаптер | Реляционная модель, миграции |
| Auth | Своя: argon2id + httpOnly-cookie + сессия в БД | Полный контроль безопасности (требование кейса) |
| Домен | `packages/core` — чистые функции + сервисы | Тестируемость без БД; переиспользование |
| Валидация | zod на границе API | Требование ARCHITECTURE §4 |
| Деплой | Docker + Helsinki VPS + Caddy + Let's Encrypt | Белый IP, HTTPS, открывается из РФ |

**Рамка принятия:** `thinking-reversibility`. Решения, которые дорого откатывать (БД, auth),
принимались максимально консервативно; обратимые (структура пакетов, токены) — быстро.

**Этап P1.1 (фундамент).** «Построй npm workspaces монорепо: packages/db (Prisma 7 +

**Этап P1.4b (страницы).** «...Мобильный 360px — first-class, не адаптация. Статусы

## 6. Ошибки ИИ и как они исправлялись

Это самый показательный раздел: воркеры уверенно сдают работу, которая не работает.

| # | Что сдал ИИ | Как нашлось | Исправление |
|---|---|---|---|
| 1 | Воркер P1.2 прислал «всё зелёное» | QA-гейт: 36/36 тестов, но в схеме и сидере остался вуз «Горизонт» | Пивот на УдГУ выполнен в том же этапе |
| 2 | `verificationSubmitSchema` принимал только латиницу | Ревью кода + живой прогон: номер билета вида `ЮР-2024-0175` не проходил валидацию — реальный студент не смог бы верифицироваться | Регулярка расширена до `\p{L}\p{N}` |
| 3 | OAuth-callback требовал `login` | **Живой прогон HTTP** (52 юнит-теста это пропустили): регистрация через VK/MAX/Telegram без логина падала с 400, хотя BRIEF v2 делает обязательными только ФИО и группу | Логин сделан необязательным, выводится из аккаунта провайдера; регрессионный тест |
| 4 | `GET /api/auth/csrf` отдавал 500 | Живой прогон: причина не в коде маршрута (в изоляции работает), а в устаревшем `.next` — прод-сборка перезаписала dev-каталог | Вывод для процесса: **окончательная проверка только на чистой прод-сборке** |
| 5 | 17 интерактивных ссылок с Hit-областью 17–22 px | **Браузер на 360 px**: нарушение WCAG 2.2 AA (2.5.8, норма 24 px) — юнит-тесты не видны | `TEXT_LINK_CLASS` + `min-h-6`; после правки 0 нарушений на всех экранах |
| 6 | Подписи нижней навигации переносились внутри слова («Успеваемос ть») | Скриншот дашборда | `text-[10px]` + `whitespace-nowrap` + `tracking-tight` |
| 7 | Cookie сессии с флагом `Secure` при работе по HTTP | **Выкладка на прод**: `/staff` отдавал 307 вместо 404, `/api/grades` — 401; браузер не отправляет Secure-cookie по HTTP | `SESSION_COOKIE_SECURE` — явный флаг; плюс поднят HTTPS (Caddy + LE), поэтому Secure работает как задумано |
| 8 | Воркер сам дописал в мой лог раздел «приёмка» | Ревью дерева перед коммитом | Самоприёмка не допускается: раздел удалён, факты перенесены с пометкой источника |
| 9 | Внешний актор коммитил моё незавершённое дерево | `git log` + reflog | Зафиксировано в логе; дальнейшие коммиты — только после зелёного QA-гейта |

## 7. Как устроены вход, данные и защита (простыми словами)

**Вход.** Студент вводит логин и пароль. Пароль сверяется с argon2id-хешем в базе —
сам пароль нигде не хранится. При успехе создаётся сессия: случайный 32-байтный токен,
в базу пишется только его SHA-256-хеш, а сам токен уезжает в httpOnly-cookie. Cookie не
доступна JavaScript, поэтому XSS не сможет её украсть. CSRF-токен (двойная отправка:
cookie + заголовок) защищает все изменения. На вход стоит rate-limit: 5 неуспешных попыток
за 15 минут на пару (логин, IP).

**Регистрация.** Через VK ID / MAX / Telegram — в прототипе это **эмуляция** согласия
(реальных ключей провайдеров нет и не нужны). Студент указывает ФИО и группу. Занятый логин
не приводит к привязке провайдера: в эмуляции провайдер не подтверждает владение логином,
иначе можно было бы зайти в чужой кабинет, зная логин.

**Верификация.** Студент загружает фото студбилета и вводит его номер. Фото попадает в
**приватное хранилище вне webroot** (Next.js отдаёт как статику только `public/`), прямой
ссылки на него нет. «Распознавание» — честный мок: он ищет номер в синтетическом реестре и
возвращает поля оттуда, ничего не выдумывая; если номера нет — отказ. Решение принимает
сотрудник деканата. **До сверки закрыты успеваемость и переписка** — иначе оценки утекли бы
людому, который не доказал, что он студент.

**Защита данных.** Главное правило: ни один серверный сервис не принимает «чужой»
идентификатор. Все функции получают сессию и сами находят `studentId` владельца.
Единственная точка сравнения — `requireOwnStudent`. Если студент подставляет в URL чужой
идентификатор, он получает **404, а не 403**: ответ «есть, но не ваш» подтверждал бы
существование чужих данных и превращал API в оракул для перебора. `/staff` и `/admin`
студент тоже не видит (404). Это проверяется тестами IDOR и вручную подстановкой ID.

**Секреты.** Только в переменных окружения на сервере. В браузере — только httpOnly-cookie
сессии. В репозитории секретов нет (проверялось грепом).
