### Этап 4a (завершён). P1.4a «Серверный слой» — живой прогон и правка OAuth (параллельная сессия)

> Исполнитель — параллельная сессия Hermes (интерактивная main-сессия владельца,
> поднятая heartbeat-задачей; процесс-владелец LSP/воркеров — PID 8151). Раздел
> сохранён её авторством: это её отчёт о её ветке и её находках.

- Ветка `feat/api-auth`, исполнитель — OpenCode. Смерж в `master` через `--no-ff`
  (`2ffe290`), запушен.
- **QA-гейт Hermes — не только юнит-тесты, но и живой прогон HTTP на прод-сборке**
  (`npm run build` + `npm run start`), потому что 52 юнит-теста воркера пропустили
  два дефекта, видимых только в живом HTTP:
  1. **OAuth-callback требовал `login`**, хотя BRIEF v2 делает обязательными только ФИО
     и группу. Регистрация через провайдера без логина падала с 400 `INVALID_INPUT`.
     Исправлено: логин необязателен, при отсутствии выводится из аккаунта провайдера.
     Добавлен регрессионный тест «callback: логин НЕ обязателен» (две независимые
     регистрации без логина → обе 200).
  2. **`GET /api/auth/csrf` отдавал 500 в dev.** Причина — не код маршрута (он работает
     в изоляции), а устаревший `.next`: прод-сборка перезаписала dev-каталог, dev-сервер
     отдавал `Cannot find module './846.js'`. В прод-пуке роут отдаёт 200. Вывод для
     процесса: **окончательная проверка всегда на прод-сборке**, dev-артефакты `.next`
     не являются доказательством.
- **Живой прогон на прод-сборке (реальный вывод curl):**
  - `POST /api/auth/login` (student1/password123) → 200 + Set-Cookie;
  - неверный пароль и несуществующий логин → **одинаковый** 401 «Неверный логин или
    пароль» (нет перебора пользователей);
  - `GET /api/requests/<id заявки student1>` с сессией student2 → **404** (не 403 —
    не раскрывает существование);
  - `/staff` и `/admin` с сессией студента → **404**;
  - `/api/grades` для неверифицированного student2 → 403 `VERIFICATION_REQUIRED`;
    для student1 → 200, 16 записей, 2 семестра, сводка avg 3.8 / 1 долг / тренд UP;
  - POST без CSRF-токена → 403; с токеном → заявка и отметка «болею» создаются;
  - валидация периода болезни (dateFrom > dateTo) → 400 с понятным текстом;
  - OAuth: неизвестный провайдер → 404; полный поток start→callback без логина → 200.
- **Итог:** `npm test` → **201/201** (22 db + 126 core + 53 web), `npm run build` зелёно,
  typecheck в 4 воркспейсах зелёный, секретов нет.
- **Принятые воркером решения (для аудита):** CSRF-cookie выдаётся публично (иначе
  клиент не получит токен до входа); занятый логин в OAuth-callback → 409, а не
  привязка (в эмуляции провайдер не подтверждает владение логином — иначе можно было
  бы зайти в чужой кабинет); ошибки владения обобщены, ошибки валидации своих данных —
  сохраняются как подсказки.
- **Дополнительные Security-решения воркера, подтверждённые ревью Hermes:**
  при неизвестном логине пароль всё равно сверяется с фиктивным хешем (выравнивание
  тайминга — нет оракула перебора логинов); одноразовый `state` OAuth гасится через
  `updateMany ... where consumedAt = null` (защита от гонки при параллельном
  использовании); быстрый отсев формата/размера файла на границе API до обращения
  к хранилищу.
- **Правка ядра, принятая:** регулярка номера студбилета расширена до `\p{L}\p{N}` —
  коды направлений УдГУ содержат кириллицу («ПИ-2023-0138»); без этой правки реальный
  студент не смог бы верифицироваться. Добавлен сервис `services/teachers.ts`.

### Этап 6 (завершён). P4-часть — выкладка на Helsinki VPS + HTTPS

Исполнитель: Hermes (ручная работа, не воркер — здесь секреты и доступы).

- **Инфраструктура:** Helsinki VPS `177.3.196.28` (Docker, 2 ГБ RAM). Внешний актор
  ранее включил `ufw` с политикой DROP — из-за этого порты 80/443 были закрыты и
  Let's Encrypt не мог достучаться (`Timeout during connect`). Открыты `80/tcp`
  и `443/tcp`. Параллельно поднят Caddy (systemd, автостарт) с обратным прокси
  на `127.0.0.1:3000`.
- **Домен:** своего домена нет, поэтому использован сервис wildcard-DNS
  `177-3-196-28.nip.io` → резолвится в IP VPS. Caddy автоматически получил
  сертификат Let's Encrypt. Итог: **https://177-3-196-28.nip.io/** (HTTP отдаёт
  308-редирект на HTTPS). Ссылка работает из России без VPN.
- **Стек прода:** контейнеры `udgu-db` (postgres:16, том `udgu-db-data`) и
  `udgu-web` (образ собран из `apps/web/Dockerfile`, том `udgu-storage-data`),
  оба с `restart=unless-stopped`, в одной docker-сети. Порт БД опубликован
  **только на 127.0.0.1** VPS — из интернета недоступен.
- **Секреты:** `.env` с `POSTGRES_PASSWORD` (сгенерирован `secrets.token_urlsafe(24)`)
  лежит ТОЛЬКО на VPS в `/opt/udgu-deanery/.env` (chmod 600). В репозитории и в
  образе секретов нет. Миграции и сидер применены с главного сервера через
  SSH-туннель (`ssh -L 5433:127.0.0.1:5432`) — БД снаружи не публикуется.
- **Перенос образа:** `docker save | gzip | ssh docker load` (Docker Hub не нужен).
- **Проверка живым прогоном на проде** (`curl` + браузер 360 px): health с реальной
  проверкой БД; login student1/student2 → 200; все 12 страниц → 200; IDOR

  гейт верификации (student2 → /api/grades) → **403 VERIFICATION_REQUIRED**;

  Referrer-Policy, Permissions-Policy); PWA manifest и service worker отдаются.
- **Устойчивость:** полный рестарт стека (`docker restart udgu-db udgu-web`) →
  здоровье восстанавливается, данные сохраняются (22 пользователя, 443 пары,
  65 оценок, 4 верификации).

**Ошибка, найденная именно на выкладке (её не видели 263 юнит-теста):** при работе
по plain HTTP cookie сессии имела флаг `Secure` (потому что `NODE_ENV=production`),
а браузер и curl **не отправляют** Secure-cookie по HTTP. Внешне это выглядело как
«все разлогинены»: `/staff` отдавал 307 вместо 404, `/api/grades` — 401 вместо
данных. Исправлено: флаг управляется явной переменной `SESSION_COOKIE_SECURE`
(по умолчанию в продакшене включён — безопасное значение), плюс поднят HTTPS,
 поэтому Secure-cookie работает как задумано. Регрессионный тест добавлен.

**Урок для процесса:** окружение `production` ≠ окружение HTTPS. Окончательная
проверка работающего прототипа должна идти по реальному URL на прод-сборке —
локальный `npm test` и даже локальный `npm run build` не показывают класс
дефектов, который возникает только в сети (cookie-флаги, заголовки, редиректы,
туннели, файрволы).
